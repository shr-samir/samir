# Fundamentals: how this site works without the abstractions

Tools like React and Vite hide how the web actually works. This site uses the
platform directly, so this doc explains the platform as it shows up here: what
the browser does, what a framework would normally do for you, and where each
piece lives in our code.

It explains **concepts that hold across every feature**. What a specific feature
or layer is doing, and questions about it, live in that feature doc's
*Understanding* section (e.g. [F1a](features/F1a-design-tokens-and-fonts.md#understanding)).
Sections for work not built yet are marked *coming*.

## TL;DR

- The browser understands only **HTML, CSS and JavaScript**, and it only ever
  receives **files**. It doesn't care how they were made.
- Our TypeScript mostly runs **on our machine at build time**, in Node, and
  writes HTML files. That TypeScript never reaches the browser, so it's never
  converted to JavaScript; only its output (HTML) ships.
- We build instead of hand-writing HTML to avoid **repetition**: shared page
  parts, one template for many pages, derived pages (sitemap, RSS), and checks.
- Output is **separate files** (HTML, one CSS file, fonts, a few small scripts),
  not a bundle. The browser fetches them in parallel.
- Only browser scripts (from F3) are TypeScript compiled to JavaScript, one file
  each, loaded as native ES modules.

---

## 1. The browser only ever receives files

When someone opens a URL:

1. The browser asks a server for that URL over HTTP.
2. The server answers with a file, usually HTML.
3. The browser reads the HTML **top to bottom**. When it meets a reference to
   another file (`<link rel="stylesheet">`, `<script>`, `<img>`, a font inside
   CSS), it starts downloading it **in parallel** and keeps reading.
4. It **waits for the CSS before painting**, so visitors never see an unstyled
   page. Module scripts run after the HTML has been fully read, so they never
   hold the page up.

So HTML comes first and the rest follows, but the downloads overlap rather than
queue one after another.

The browser doesn't know or care whether a file was typed by hand, generated by
React, or written by our build script. **A website is a folder of files plus a
server that hands them out.**

## 2. Two ways to get HTML to the browser

| | Typical React + Vite app (single-page app) | This site (static) |
|---|---|---|
| HTML the server sends | Almost empty: `<div id="root"></div>` plus a `<script>` | The finished page, with all its text |
| Who builds the page | JavaScript in the visitor's browser, after downloading and running a bundle | Our build script, once, before deploying |
| Without JavaScript | Blank page | Everything readable |
| What search engines and link previews see | Whatever they manage after running the JavaScript | The real content, immediately |

**Try it:** open any page of this site and use *View Source* (Ctrl+U), not
DevTools. View Source shows exactly what the server sent. On a single-page app
you'd see an empty `<div>`; here you see the whole page. DevTools' *Elements*
panel shows the page *after* scripts have run, which hides the difference.

(React can also render on a server, e.g. with Next.js. That's the same idea as
ours, with a framework doing the rendering.)

## 3. Three moments: build time, request time, run time

Keeping these apart explains most of the design:

| Moment | Where code runs | In this site |
|---|---|---|
| **Build time** | On your machine or the host's build server, once per deploy | `scripts/build.ts` turns TypeScript page functions into `.html` files |
| **Request time** | On a server, on every visit | Nothing. The host just sends files, which is why a traffic spike costs nothing |
| **Run time** | In the visitor's browser | Almost nothing: small scripts for the theme toggle and live widgets (*coming*, F3+) |

A React single-page app does most of its work at run time, on the visitor's
device. We do almost everything at build time, on ours.

## 4. Why build at all, instead of writing HTML by hand?

For one or two pages, hand-written HTML is perfectly valid and simpler. The
browser can't tell the difference. A build pays off as the site grows, because
of **repetition**:

1. **Shared parts.** Every page needs the same `<head>`, header, nav and footer.
   Hand-written, they're copied into every file, and adding a nav link means
   editing 50 files. With a build, the header is one function every page calls.
2. **One template, many pages.** A blog post is a Markdown file holding just
   its text. The build combines each one with the post template, like a mail
   merge. The 51st post is one new file, not a copied HTML page.
3. **Derived pages.** The blog index, tag pages, sitemap and RSS all list the
   posts. The build works them out, so adding a post updates all of them. The
   resume is generated from the same data as the About page, so they can't
   disagree.
4. **Checks.** Hand-written HTML never warns you. The build fails on a missing
   title, a duplicate title, skipped heading levels or an image without alt text.
5. **Safety and config.** Text is escaped automatically (§8), and turning a
   feature off in `site.config.ts` removes it from every page, the nav and the
   sitemap at once.

**"Dynamic", but at build time.** The content is data-driven, yet the HTML is the
same for every visitor until the next deploy:

| | Changes when | Handled by |
|---|---|---|
| Build-time data (posts, projects, nav, bio) | You edit a file and redeploy | The build: it's already in the HTML |
| Truly dynamic data (local time, counters, theme choice) | Every visit or every second | Small browser scripts, after load |

The build is a tool for **the author**, not something the visitor experiences.

## 5. "Building" is writing files

Vite's core job is to turn your source into files a browser can load. Strip
away the extras (hot reload, plugins, bundling) and that is: **read some input,
produce some text, write it to disk.** Node can do that with its built-in `fs`
module, so our build is an ordinary program:

```
src/pages/index.ts   a function that returns the page as HTML text
        │
        ▼
scripts/build.ts     Node calls each page function and writes the text
        │            to dist/index.html, dist/about/index.html, …
        ▼
dist/                plain files, ready for any static host
```

**Nothing is bundled into one file.** By the end of F1a, `dist/` holds separate
files that the HTML links to:

```
dist/
  index.html          the page
  site.css            all CSS joined into one file (the only joining we do)
  fonts/*.woff2       copied as-is
  client/*.js         compiled browser scripts (from F3)
```

**Where:** [`scripts/build.ts`](../scripts/build.ts); step-by-step walkthrough in
the [F1a feature doc](features/F1a-design-tokens-and-fonts.md#how-it-works).

## 6. Two kinds of TypeScript

It's easy to assume "the browser can't read TypeScript, so the build converts it
all to JavaScript". Here, most TypeScript is **the program that makes the
pages**, like a recipe: it stays in the kitchen, and only the cake (HTML) is
served.

| | Build-time TypeScript | Browser TypeScript (*coming*, F3) |
|---|---|---|
| Where | `scripts/`, `src/pages/`, `src/lib/` | `src/client/` |
| Runs in | Node, on our machine | The visitor's browser |
| Converted to JavaScript? | **No.** Node strips the types in memory and runs it (§10) | **Yes**, by `tsc`, into `dist/client/*.js` |
| Reaches the browser? | **Never.** Only its output (HTML) does | Yes, as `.js` files |

## 7. Templates without JSX: tagged template literals

In React you write JSX:

```jsx
<h1>{title}</h1>
```

Browsers can't run JSX. A compiler (Babel, esbuild inside Vite) rewrites it into
function calls like `jsx("h1", { children: title })`, which build JavaScript
objects that React then turns into DOM elements.

We use a plain JavaScript feature instead, the **tagged template literal**:

```ts
html`<h1>${title}</h1>`
```

A function name placed right before a backtick string gets called with the
string split into its fixed parts and the values separately. For
``html`<h1>${name}</h1><p>${3}</p>` `` with `name = "<b>"`, the function receives:

```js
strings: ["<h1>", "</h1><p>", "</p>"]   // the parts written in our source
values:  ["<b>", 3]                     // what was inside ${ }
```

Because the fixed parts and the values arrive separately, the function knows
which is which. The fixed parts are markup we wrote, so they're trusted. The
values might come from content or config, so they get **escaped** before
everything is joined into one string. No compiler, no runtime, no virtual DOM:
the result is just text.

**Where:** [`src/lib/html.ts`](../src/lib/html.ts).

## 8. Escaping: the safety React gives you silently

If text from a blog title were inserted raw, a title like
`<script>steal()</script>` would become a real script: that attack is called
cross-site scripting (XSS). The fix is **escaping**: replacing the five
characters that mean something in HTML with *entities* the browser displays as
text:

| Character | Becomes | Why it matters |
|---|---|---|
| `<` `>` | `&lt;` `&gt;` | Would start or end a tag |
| `&` | `&amp;` | Would start an entity |
| `"` `'` | `&quot;` `&#39;` | Would end an attribute value like `title="…"` |

React does this for you automatically in JSX, which is why you rarely think
about it. Its escape hatch is `dangerouslySetInnerHTML`. Ours is the same idea:

| React | This site |
|---|---|
| `{title}` (escaped automatically) | `${title}` inside `html` (escaped automatically) |
| `dangerouslySetInnerHTML={{ __html: markup }}` | `${raw(markup)}` |
| Nested components aren't escaped twice | Nested `html` fragments aren't escaped twice |

**Where:** [`src/lib/html.ts`](../src/lib/html.ts), tested in
[`html.test.ts`](../src/lib/html.test.ts).

## 9. Routing without a router: folders are URLs

A single-page app has one real HTML file. React Router reads the address bar in
JavaScript and swaps what's on screen, so `/about` never exists as a file.

Static hosting uses the oldest routing there is: **the URL is a path to a
file**. When a browser asks for `/about/`, most static hosts serve
`about/index.html` from the site folder. So the build writes each page as a
folder with an `index.html`:

| URL | File in `dist/` |
|---|---|
| `/` | `index.html` |
| `/about/` | `about/index.html` |
| `/blog/my-first-post/` | `blog/my-first-post/index.html` |

That's why every URL here ends in a slash: it names a folder. Each page is a
real document, so links are plain `<a href>` tags that do full page loads. On a
static site served from a CDN those loads are fast, and the browser handles back
buttons, scroll position and opening in a new tab for free, all things a
client-side router has to re-implement.

**Where:** `outputFile()` in [`src/lib/page.ts`](../src/lib/page.ts).

## 10. TypeScript without a compile step (for Node)

Browsers and Node only run JavaScript. TypeScript is JavaScript plus type
annotations, so for most code, turning it into JavaScript means deleting the
annotations. Since version 24.12, Node does exactly that on the fly, which is
called **type stripping**:

```ts
function add(a: number, b: number): number { return a + b; }
// Node runs it as (actual output of Node's stripper):
function add(a        , b        )         { return a + b; }
```

Node replaces types with spaces, not nothing, so line and column numbers in
error messages still match your source.

This means our build script runs with plain `node scripts/build.ts`.

**Stripping is not checking.** Node deletes the types without looking at them,
so `pnpm build` runs even when the code has type errors. Type safety comes from
running `tsc` separately (`pnpm typecheck`), which only checks and writes no
files. The deploy pipeline (F12) runs both.

Stripping only works for syntax that is purely a type annotation. Features that
generate JavaScript, like `enum`, can't simply be deleted, so they're banned by
the `erasableSyntaxOnly` setting.

**Where:** [`tsconfig.json`](../tsconfig.json).

## 11. Imports are URLs, not magic

In a Vite project you write `import { x } from "./utils"` and it works. That's
Vite (or TypeScript, or Node's old CommonJS loader) **guessing** the file:
`utils.ts`? `utils/index.ts`? The real platforms don't guess.

- **In the browser**, an import path is a URL. `./utils` means a file literally
  named `utils`, with no extension. Package names like `"react"` don't work at
  all without extra setup (an *import map*), because they aren't URLs.
- **In Node's ES modules**, the same rule applies: you name the exact file.
  Even a dynamic `import()` of a file on disk needs a `file://` URL, which is
  why the build converts Windows paths like `D:\…` with `pathToFileURL`.

So in this repo imports always include the extension: `from "#src/lib/html.ts"`. When
browser scripts are compiled (*coming*, F3), TypeScript rewrites `./x.ts` to
`./x.js` so the URL points to the file that actually exists in `dist/`.

### Absolute imports without a bundler

In a Vite project, `import { html } from "@/lib/html"` works because two tools
cooperate: tsconfig `paths` tells *TypeScript* what `@/` means, and a Vite alias
rewrites the import before anything runs. Remove Vite and only TypeScript knows
about `@/`: Node reads the import literally and crashes.

Node has its own mechanism, **subpath imports**: an `"imports"` map in
`package.json`.

```json
"imports": {
  "#src/*": "./src/*",
  "#scripts/*": "./scripts/*"
}
```

Now `import { html } from "#src/lib/html.ts"` works from any file at any depth.
Node resolves it at runtime, and TypeScript reads the same map, so both always
agree. The `#` is required; it marks "look this up in my own package", so it
can never clash with an npm package name.

The limit: **browsers don't read `package.json`**. In the browser, the
equivalent is an *import map* (`<script type="importmap">`), a JSON block in the
HTML that maps names to URLs. Browser scripts arrive in F3; until then this repo
uses `#src/…` everywhere.

### The `import type` trap

One trap: `import { SomeType } from "./x.ts"` looks harmless, but after
stripping, Node still tries to import `SomeType`, which doesn't exist in
JavaScript, and it crashes. Type-only imports must say so, as in
`import type { SomeType }`. The `verbatimModuleSyntax` setting makes `tsc`
enforce this.

## 12. JavaScript in the browser without a bundler (*coming*, F3)

Vite bundles your modules into a few files because, years ago, browsers
couldn't load modules and every file cost a slow request. Today browsers load ES
modules natively:

```html
<script type="module" src="/client/theme.js"></script>
```

- `type="module"` scripts are **deferred** automatically: they download in
  parallel and run after the HTML has been read, so they never block the page.
- `import` statements inside them fetch other modules by URL.
- With only a few small scripts, bundling saves almost nothing.

Our scripts only *enhance* a page that already works without them (PRD R4).
This section gets filled in when the first script lands.

## 13. CSS without Tailwind: design tokens and cascade layers

Tailwind generates utility classes from its configuration; CSS-in-JS generates
class names at build or run time. We use neither: plain CSS, with two platform
features doing the work a framework would otherwise do for us.

**Custom properties as design tokens.** A CSS custom property
(`--space-m: 1.5rem;`) is a variable, read anywhere with `var(--space-m)`. Every
visual value — sizes, spacing, radii, shadows, durations — is defined once in
[`tokens.ts`](../src/styles/tokens.ts), a plain TypeScript data file, and the
build turns it into these variables ([`tokens-css.ts`](../src/styles/tokens-css.ts)).
Every other stylesheet reads only `var(--…)`, never a raw number, so changing a
size means editing one file and rebuilding — the same goal Tailwind's config or
a CSS-in-JS theme object serves, without a build plugin.

**Cascade layers instead of specificity fights.** Normally two rules that match
the same element fight by *specificity* (an ID beats a class beats an element),
which is why frameworks reach for `!important` or scoped class names to force an
order. `@layer` sidesteps this: layers are declared once, in order —

```css
@layer reset, tokens, base, layout, components, utilities;
```

— and **a rule in a later layer always wins, no matter how specific the earlier
one is**. A single-element selector in `utilities` beats three chained classes
in `base`. Each source file ([`reset.css`](../src/styles/reset.css),
[`base.css`](../src/styles/base.css), …) declares which layer it belongs to, and
the build concatenates them in that order into one `site.css` (§5). This is why
component and utility CSS, arriving in later features, never needs to
out-specify what F1a writes now.

**Fluid sizes with `clamp()`.** A type size that jumps at a breakpoint looks
abrupt. `clamp(min, preferred, max)` picks the middle value unless it would go
outside `min`/`max`, so a size can grow smoothly with the viewport instead of
stepping. The preferred value mixes `rem` (ties the size to the user's font
setting) and `vw` (ties it to viewport width), so text still grows when the user
zooms, which a pure-`vw` value barely would (WCAG 1.4.4).

There's a catch: zooming makes each CSS pixel bigger, so the *viewport in CSS
pixels* shrinks, and the `vw` part shrinks with it. A fluid heading therefore
grows less than the zoom level: on a 1280px window at 200% zoom, `text-4xl`
renders at about 164% of its normal size and reaches 200% only around 300% zoom.
Fixed sizes (`text-base`, `text-prose`) double exactly. The rule that keeps 200%
reachable within the browser's 500% zoom limit is `max ≤ 2.5 × min`, and a test
enforces it ([F1a X6](features/F1a-design-tokens-and-fonts.md#discovered-checklist)).
The math: [`fluid.ts`](../src/styles/fluid.ts).

- **Where:** [`src/styles/tokens.ts`](../src/styles/tokens.ts) (data),
  [`tokens-css.ts`](../src/styles/tokens-css.ts) (CSS generation),
  [`fluid.ts`](../src/styles/fluid.ts) (clamp math),
  [`stylesheet.ts`](../src/styles/stylesheet.ts) (layer order and concatenation).


**Colors in OKLCH.** Hex (`#1a5fb4`) and HSL describe colors the way screens
mix them, not the way eyes see them: an HSL yellow and blue at "50% lightness"
look nothing alike in brightness. OKLCH (`oklch(50% 0.15 255)`: lightness,
chroma, hue) is built so equal lightness *looks* equally bright across hues.
That lets the palette give every role a fixed lightness and swap the hue for
each accent, with contrast staying almost the same.

**Themes with `light-dark()`, no JavaScript.** `color-scheme: light dark` on the
page tells the browser both themes are supported, and `light-dark(A, B)` picks A
or B from the visitor's OS preference. Each color token is written that way, so
the page follows the OS theme on its own. Setting `color-scheme: dark` on any
element forces its subtree dark, which is how the demo page shows light and dark
panels side by side and how the theme switcher (F3) will work.

One subtlety: an inherited property like `color` is resolved on the parent,
with the parent's theme. A child that changes its `color-scheme` must restate
`color: var(--color-text)` to pick up its own value.

**Contrast is computed, not eyeballed.** WCAG contrast compares how much light
two colors emit (relative luminance) as `(lighter + 0.05) / (darker + 0.05)`,
from 1:1 to 21:1. AA needs 4.5:1 for text and 3:1 for borders and focus
indicators. The build converts every palette color from OKLCH to the light a
screen emits and checks every required pair; a failure stops the build. It
also rejects colors a normal (sRGB) screen can't display, since the browser
would silently substitute a different color and the computed contrast would be
wrong. → [`color.ts`](../src/styles/color.ts), [`palette.ts`](../src/styles/palette.ts)

## 14. Fonts: when they download, and why text doesn't jump

With a framework you'd import a font package (or Next.js `next/font`) and it
would do all of this for you. Underneath, it's four platform features.

**`@font-face` declares, it doesn't download.** A rule like

```css
@font-face {
  font-family: "Geist";
  src: url("/fonts/geist-latin-wght-normal.woff2") format("woff2");
  font-style: italic;
}
```

only tells the browser where the italic Geist file *would* be. The browser
fetches it once some text on the page is rendered in Geist italic. So a site can
declare italic and code fonts everywhere and still download them only on pages
that use them. This site's home page downloads one font file; a page without
italics never fetches the italic file.

**Variable fonts: one file, every weight.** A variable font holds a continuous
weight axis (here 100–900), so regular and bold come from the same file instead
of one file each. `font-weight: 100 900` in the `@font-face` tells the browser
that range is inside.

**`font-display: swap`: never hide text.** Without it, browsers may hide text
for up to a few seconds while a font downloads. `swap` shows text immediately
in the next font in the list and replaces it when the web font arrives.

**Why text jumps, and the fix.** The fallback (Arial, say) has different letter
widths and line metrics than the web font, so the swap can re-wrap lines and
push everything below down: *layout shift*, which is jarring and hurts the CLS
score. CSS lets a fallback face be reshaped to match:

```css
@font-face {
  font-family: "Geist Fallback";
  src: local("Arial");
  size-adjust: 102.19%;       /* Geist is 2.19% wider than Arial */
  ascent-override: 98.35%;    /* Geist's space above the baseline */
  descent-override: 28.87%;   /* and below it */
}
```

and `font-family: "Geist", "Geist Fallback", sans-serif` uses it while Geist
loads. Measured here: a paragraph is 92px tall in Geist, 92px in the tuned
fallback, 84px in plain Arial. (Safari ignores the two overrides, so it may
still shift slightly.) Next.js's `next/font` generates exactly this kind of
fallback face for you.

**Preload the one file every page needs.** Normally the browser discovers a
font only after downloading and parsing the CSS. A
`<link rel="preload" as="font" crossorigin>` in the `<head>` starts that
download right away. Fonts need `crossorigin` even from your own domain,
because fonts are always fetched in CORS mode.

- **Where:** [`fonts.css`](../src/styles/fonts.css),
  [`document.ts`](../src/layout/document.ts) (preload),
  [`font-metrics.ts`](../scripts/font-metrics.ts) (reading metrics from the file).
